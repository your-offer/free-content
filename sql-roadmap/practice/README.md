Все данные и условия здесь синтетические. Это учебные задачи «Твоего оффера», а не реальные события пользователей или вопросы конкретного работодателя.

## Как запустить

Нужны PostgreSQL 15+ и любое учебное соединение: локальная база, учебная PostgreSQL-песочница или SQL-редактор с таким подключением.

1. Открой [dataset.sql](dataset.sql) и выполни его целиком в отдельном учебном соединении.
2. Решай задачи ниже **в том же соединении**. Данные находятся во временных таблицах и исчезнут при его закрытии. Если редактор создаёт новое соединение для каждого запуска, отправляй датасет и свой запрос одним скриптом в новом соединении.
3. Для повторного запуска датасета открой новое соединение. Скрипт не удаляет существующие таблицы.
4. После самостоятельной попытки сравни результат с контрольными значениями и открой [solutions.sql](solutions.sql).

Если PostgreSQL пока не установлен, сначала проходи задачи PostgreSQL Exercises из роадмапа: они работают в браузере без регистрации. Сам этот практикум — набор SQL-файлов, не онлайн-тренажёр.

## Что хранится в таблицах

| Таблица | Одна строка | Особенности |
|---|---|---|
| `pa_users` | Пользователь | `user_id` уникален; `channel` может быть NULL |
| `pa_orders` | Заказ | Сумма в условных денежных единицах; статус `paid`, `refunded`, `cancelled` или `pending` |
| `pa_events_raw` | Загрузка события | `ingest_id` уникален; `event_id` повторяется при повторной доставке; бывают анонимные события |

Поля времени — `timestamptz`. Все задачи, кроме сравнения часовых поясов в Q7, используют UTC.

Основной период: **с 1 ноября 2026, 00:00 UTC включительно до 5 ноября 2026, 00:00 UTC не включительно**. В данных намеренно есть записи за пределами периода.

Для финансовых задач учитываем только заказы со статусом `paid` и временем `paid_at` внутри периода. `refunded` целиком исключаем: здесь используем упрощённое определение выручки по текущему статусу, без бухгалтерского учёта частичных возвратов. `purchase` в событиях — действие интерфейса, оно не подтверждает оплату и не заменяет таблицу заказов.

## Q1. Дедупликация

Оставь одну версию каждого `event_id`: с самым поздним `ingested_at`; при равенстве выбери наибольший `ingest_id`. Выведи `event_id`, `user_id`, `event_name`, `event_at`. Здесь обрабатываем **все** события, не ограничивая период.

Проверь, сколько строк было до и после; объясни, почему `DISTINCT` по всем полям не уберёт повторную загрузку.

## Q2. Пользователи без оплат

Для каждого пользователя посчитай количество оплаченных заказов и выручку в основном периоде. Сохрани пользователей без оплат: у них должны быть нули. Отсортируй по `user_id`.

Проверь, что не потерял пользователей 3 и 6. Почему `COUNT(*)` после LEFT JOIN не подходит для подсчёта их заказов?

## Q3. Равные места в рейтинге

Среди плативших пользователей выведи **два наибольших различных уровня выручки** за основной период. Если несколько пользователей имеют одинаковую выручку, включи всех. Выведи `user_id`, `revenue`, `revenue_rank`, отсортируй по месту и ID.

Объясни, чем ответ отличается от «ровно два пользователя» и от отбора `RANK() <= 2` на других данных.

## Q4. Финансовые метрики

За основной период рассчитай:

- Выручку, число оплаченных заказов и число плативших пользователей.
- Число активных пользователей: уникальные известные `user_id` с любым событием в периоде. Анонимные события не учитывай.
- Средний чек: выручка / число оплаченных заказов.
- ARPPU: выручка / число плативших пользователей.
- ARPU активных: выручка **именно активных пользователей** / число активных пользователей.

Округли отношения до двух знаков. Если знаменатель нулевой, верни NULL: значение метрики не определено. Выручка при отсутствии оплат равна нулю. Не соединяй сырые заказы с сырыми событиями для подсчёта денег.

## Q5. Календарный D1 retention

Когорта — дата регистрации в UTC. Возврат D1 — хотя бы одно событие известного пользователя **на следующий календарный день**, а не в течение следующих 24 часов и не в любой будущий день.

Считай, что данные полны только до **5 ноября, 00:00 UTC**. Включи когорты регистрации начиная с 1 ноября, у которых следующий календарный день полностью закончился к этой границе. Выведи дату когорты, её размер, число вернувшихся и процент D1 retention.

Размер когорты берётся из регистраций. Пользователь без активности на D1 остаётся в знаменателе. Повторные события не увеличивают число вернувшихся. Объясни, почему когорта 4 ноября не должна получить нулевой retention в этом отчёте.

## Q6. Последовательная воронка

За основной период посчитай число уникальных известных пользователей на шагах **view → checkout → purchase** и конверсию из первого шага в третий.

Правила:

- Цепочка должна проходить в пределах одного календарного дня UTC.
- Каждый следующий шаг строго позже предыдущего. Одинаковое время не подтверждает последовательность.
- Пользователь считается один раз на шаг за весь период, даже если прошёл его несколько раз или в разные дни.
- Для третьего шага нужно завершить всю цепочку; наличие purchase само по себе недостаточно.
- Повторы доставки не увеличивают счётчики. Если нет ни одного view, конверсия — NULL.

Проверь пользователя 2: checkout у него раньше view. У пользователя 3 purchase случился на следующий день. У пользователя 4 есть checkout одновременно с view и ещё один позже — нужно найти допустимую цепочку.

В эталоне для этой задачи одинаковые `(user_id, event_name, event_at)` схлопываются: это сохраняет ответ при заданном правиле строгого времени. Для универсального учёта событий с обновлениями используй бизнес-ключ и правило Q1.

## Q7. Граница месяца

Сравни выручку за календарный ноябрь по UTC и по `Europe/Moscow`. Статус оплаты остаётся тем же. Выведи два числа.

Особое внимание — заказу 107 в `2026-11-30 23:30 UTC` и заказу 108 ровно в `2026-12-01 00:00 UTC`. Объясни, почему нельзя полагаться на случайный часовой пояс SQL-сессии.

## Q8. Дни без оплат и оконная рамка

Построй по одному ряду на каждый день 1–4 ноября UTC: выручка за день, накопительная выручка и среднее за текущий и два предыдущих дня.

День без оплат должен иметь нулевую выручку. В начале периода среднее считай по доступным дням: для 1 ноября окно из одного дня, для 2 ноября — из двух. Это явное условие задачи, а не универсальное правило скользящего среднего.

## Как разбирать ошибки

Для каждой задачи сначала проверь состав строк и ключи, затем значения. Совпадение одного итогового числа ещё не доказывает правильность: сравни промежуточные выборки и придумай контрпример.

Попробуй изменить данные: добавить дубль события, пользователя без заказов, оплату ровно на правой границе периода или одинаковую выручку нескольким людям. Предскажи изменение результата до запуска запроса.
