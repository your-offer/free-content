# SQL-задачи по мотивам собеседований

[← К роадмапу](../) · [Учебный практикум с данными и решениями](../practice/)

Эта подборка составлена по записям из базы собеседований автора. Название компании показывает, к какой записи относится исходная идея; мы не проверяли, что именно в такой формулировке вопрос задавал работодатель. Схемы, условия и граничные случаи ниже переработаны для самостоятельной практики. Это **10 учебных постановок**, а не готовый SQL-тренажёр: данные и эталонные запросы для них не прилагаются.

Пиши на PostgreSQL. Перед каждым запросом назови ключ таблицы, уровень строки и период. После решения придумай маленький набор данных, на котором сломается неверный подход: дубли, `NULL`, равные времена, нулевые значения или пустой месяц. Первые четыре задачи подходят для разминки; остальные ближе к Middle.

## Разминка

### 1. Повторные события · запись Т-Банка

`user_logs(user_id, occurred_at)` — одна строка на запись лога; одинаковая пара полей может встречаться несколько раз. Выведи `user_id`, `occurred_at` и `copies` только для пар с `copies > 1`. Отсортируй по числу копий по убыванию, затем по ID и времени. **Проверка:** две записи одного пользователя в разные моменты не являются дублем; одинаковое время у разных пользователей тоже не является дублем.

Темы: `GROUP BY`, `HAVING`, уровень детализации.

### 2. Клиенты с крупными оплатами · запись Яндекса

`orders(order_id, customer_id, paid_at, amount, status)`; `order_id` уникален, время хранится как `timestamptz`. Найди клиентов, у которых **более четырёх** заказов со статусом `paid` за календарный 2024 год по UTC и сумма этих заказов **строго больше 20 000**. Выведи `customer_id`, `paid_orders`, `revenue`. **Проверка:** заказ ровно на правой границе года исключается; отменённый заказ не входит ни в количество, ни в сумму.

Темы: фильтр периода, агрегаты, `HAVING`, два независимых порога.

### 3. Сотрудник получает больше руководителя · запись Wildberries

`employees(employee_id, boss_id, salary)`; `employee_id` уникален, `boss_id` ссылается на другую строку этой же таблицы и может быть `NULL`. Выведи `employee_id`, `salary`, `boss_id`, `boss_salary` для сотрудников, чья зарплата **строго выше** зарплаты непосредственного руководителя. **Проверка:** руководители без начальника и равные зарплаты в ответ не входят. Реши через соединение таблицы с самой собой.

Темы: self join, сравнение строк, `NULL`.

### 4. Первая успешная транзакция · запись Т-Банка

`transactions(transaction_id, customer_id, amount_rub, success, occurred_at)`; `transaction_id` уникален. Оставь клиентов, у которых общая сумма **успешных** транзакций строго больше 100 000 ₽. Для каждого выведи первую успешную транзакцию: `customer_id`, `transaction_id`, `amount_rub`, `occurred_at`. При равном времени первой считай транзакцию с меньшим `transaction_id`. **Проверка:** неудачные транзакции не влияют ни на порог, ни на выбор первой. Попробуй решить задачу с оконной функцией и без неё.

Темы: CTE, агрегаты, `ROW_NUMBER`, детерминированный порядок.

## Ближе к Middle

### 5. Заказы в соседние дни · запись Яндекса

`orders(order_id, user_id, created_at)`; `created_at` — `timestamptz`. Найди пользователей, сделавших заказы **как минимум в два последовательных календарных дня UTC**. Верни по одной строке на `user_id`. **Проверка:** два заказа в один день не образуют серию; заказы 31 декабря и 1 января образуют. Сначала получи уникальные пары «пользователь — дата», затем сравни соседние даты.

Темы: даты, дедупликация, `LAG`.

### 6. Пересекающиеся поездки машины · запись Яндекса

`rides(ride_id, car_id, start_at, end_at)`; все времена заданы, `start_at < end_at`. Интервал поездки — **`[start_at, end_at)`**. Найди пары разных поездок одной машины, которые действительно пересекаются. Выведи `car_id`, `ride_id_1`, `ride_id_2`, где `ride_id_1 < ride_id_2`, чтобы не получить пару дважды. **Проверка:** если одна поездка закончилась ровно в момент начала другой, пересечения нет; вложенные интервалы пересекаются.

Темы: self join, неравенства, границы интервалов.

### 7. Товар на момент заказа · запись Wildberries

`item_versions(item_id, valid_from, item_name, price)` хранит историю свойств товара; пара `(item_id, valid_from)` уникальна, версия действует с `valid_from` до начала следующей версии. `orders(order_id, item_id, ordered_at)` хранит заказы. Для каждого заказа выведи `order_id`, название и цену товара, действовавшие **в момент заказа**. Если версия до заказа неизвестна, сохрани заказ с `NULL` в полях товара. **Проверка:** нельзя присоединять просто последнюю версию на сегодня; обновление ровно в `ordered_at` уже действует.

Темы: соединение с историей, последнее значение на дату, `LEFT JOIN`.

### 8. Конверсия виджета · запись Ozon

`events(event_id, user_id, event_at, page_url, action_type, widget_id)`; `event_id` уникален, `user_id` может быть `NULL`. Для страницы `/catalog` и виджета `522955` рассчитай по календарным дням UTC число уникальных известных пользователей с просмотром (`view`), число из них с **более поздним кликом** (`click`) в тот же день и конверсию из просмотра в клик. День с просмотрами без кликов оставь с нулём в числителе. **Проверка:** клик до просмотра и клик на следующий день не засчитываются; несколько событий одного пользователя не увеличивают счётчик.

Темы: воронка, порядок событий, `COUNT(DISTINCT)`, корректный знаменатель.

### 9. Регионы с малым числом оплат · запись Яндекса

`regions(region_id)`, `users(user_id, region_id)`, `payments(payment_id, user_id, paid_at, status)`; все ID уникальны в своих таблицах. Найди **до десяти** регионов с наибольшим числом успешных оплат в марте 2026 года по UTC среди регионов, где таких оплат **меньше 1 000**. Выведи `region_id`, `paid_count`; при равенстве сортируй по `region_id`. Включи регионы с нулём оплат. **Проверка:** фильтр времени и статуса не должен уничтожить пустые регионы после `LEFT JOIN`.

Темы: левое соединение, агрегаты, `HAVING`, top-N.

### 10. Доля одобренных заявок · запись Wildberries

`claims(claim_id, customer_id, created_at, status, amount_rub)`; статусы: `approved`, `rejected`, `in_progress`. По месяцу создания рассчитай долю одобренных **по количеству** и **по сумме** только среди рассмотренных заявок (`approved` и `rejected`). Затем добавь накопительные доли с января каждого календарного года. Выведи каждый месяц, в котором была хотя бы одна заявка: месяц, число рассмотренных заявок, обе месячные и обе накопительные доли. **Проверка:** `in_progress` не входит ни в числитель, ни в знаменатель; накопительная доля считается из накопленных сумм, а не как среднее месячных процентов. При нулевом знаменателе верни `NULL`.

Темы: условные агрегаты, оконные суммы, знаменатели, граница года.

## Как проверить себя

Для каждой задачи объясни вслух: что означает одна выходная строка, какие строки попадают в выборку, как обработаны равенства и пропуски, почему результат не размножается после соединений. Если нужен практикум с готовым датасетом и проверенными SQL-решениями, перейди к [Q1–Q8](../practice/).
